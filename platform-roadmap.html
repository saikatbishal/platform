Phase 1 — current

The design pass

The app currently wears the operating system’s clothes. Nothing below this phase starts first.

  1. Load the chosen typefaces UX

    Archivo for interface and display, IBM Plex Mono for figures and station codes, IBM Plex Sans Devanagari for the bilingual board. Self-host via @fontsource so the files ride the same cache as everything else, then fill the three empty --font-* slots. The single highest-leverage change on this page.

  2. Stop the font swap from jumping UX

    Set size-adjust on the fallback stack.

    Explained simplyThe browser shows a system font for a moment before your font finishes downloading. If the two take up different amounts of space, every line shifts when the swap happens. size-adjust stretches the temporary font to occupy the same space, so the swap is invisible.

  3. A real type scale UX

    One ratio, five or six sizes as tokens, line-height that varies with size — tight for display, 1.5+ for body. Kill the 9.6px label while you are in there.

  4. The two Figma screens the plan is owed UX

    The Map (desktop and 390px — decide the chrome, where stats live, what first-open shows) and Add a Journey (the fifteen-second flow, drawn before built). Twenty reference screenshots first: map UIs, transit design, collection UIs, passport aesthetics.

  5. Fix the badge, free the yellow UX

    Ink on surface, hairline border, inner radius = outer − border. The accent goes back to the route and to nothing else — the squint test’s number-one finding.

  6. The station-board component UX

    Yellow field, navy text, Devanagari above Latin. Build once; reuse as station headers and the passport card. It is the app’s logo without designing a logo.

  7. Icons that exist UX

    The manifest names 192/512/maskable icons with no files behind them. Draw the family from the board or the route mark, matching the existing favicon.

  8. Make the reward survive greyscale UX

    Widen the lightness gap between land and visited land and add a border cue, so “states unlocked” reads for colour-blind users and in daylight.

Phase 2

The map experience

The centrepiece. Most of the UI/UX hours in the whole project live here.

  1. One-handed zoom UX

    Double-tap-and-drag (the Google Maps gesture): thumb slides down to zoom in, up to zoom out. Pinch already works; this is the standing-on-a-platform gesture.

  2. Rubber-band the edges UX

    A hard fling should never strand the user in empty sea. Let the clamp stretch slightly, then settle back — an eased boundary instead of a wall.

  3. Fly-to UX

    Animate x/y/zoom along an eased path with a slight zoom-out-then-in arc — the parabolic camera move every good map uses, because it keeps context during the jump.

  4. First-open framing UX

    On a phone, fit to the journeys’ bounding box, not the whole country — which also fixes the half-empty-screen finding. Whole-country stays one “Fit” tap away.

  5. Hit-testing for taps UX

    Nearest station within 24 screen pixels, biased toward visited ones.

    Explained simplyThe map is a picture, not buttons — when someone taps, you must work out which dot they meant. Take the tap position, find the closest station in screen space, and treat a near-miss as a hit, because thumbs are imprecise.

  6. Station and journey cards UX

    Tap a station: board-style header, code, zone, times passed through. Tap a route: date, train, distance “via N stops”, the note.

  7. The accessible twin UX

    A text list of journeys as the map’s screen-reader fallback — and honestly useful in its own right as the journey log.

  8. Wire the lazy district fetch FE

    The hook and the tier flag exist; the actual fetch at zoom ≥ 4 is not connected yet.

  9. Your labels beat generic labels UX

    At state zoom and below, visited-station labels outrank city labels in the collision pass. Your places matter more than default places.

  10. The draw-in UX

    Routes draw in on first load, staggered by journey date, ~1.2s total, stations lighting up as the line reaches them. This is the shareable moment — budget real time on the easing. Under prefers-reduced-motion, it becomes an instant fade.

  11. One living dot UX

    The vermillion “you are here” gets a slow three-second breathing pulse — the only permanently animated thing on screen, which is what keeps it meaningful.

Phase 3

Logging a journey

Fifteen seconds or it is a bug. At a minute, you stop logging in week two and the product dies however good it looks.

  1. Search that knows codes UX

    Instant search over the in-memory list, matching name and code — you know it as HWH before Howrah. Prefix matches first, then contains.

  2. Zero-typing repeats UX

    Recents and frequents above the keyboard before a single letter. Most journeys reuse four stations; the repeat route should cost two taps. Plus a swap-direction button — returns are half of all journeys.

  3. Rail-aware dates UX

    Default today, yesterday one tap away — overnight trains arrive after midnight, and that detail says the app was built by someone who rides them.

  4. Train autocomplete from the timetable UX

    Given from + to, offer the trains that actually run that hop. Picking one upgrades the drawn route from “plausible” to “exact — via the 12839’s stops”, and the UI should say so.

  5. No success modal UX

    On save the sheet closes and the map draws the new route. The reward is the confirmation; a dialog in front of it would hide the only good part.

  6. Optimistic add, with undo UX

    The journey appears instantly; a quiet toast offers Undo for five seconds.

    Explained simplyInstead of making the user wait for the server to say “saved”, show the result immediately and send the save in the background. If it fails — which almost never happens — apologise then, rather than making every save feel slow to guard against a rare failure. And acting-then-offering-to-reverse feels fast, where asking-“are you sure?”-before-acting feels bureaucratic.

  7. Copy in a human voice UX

    “These are the same station” beats “Invalid input”. Every error says what happened and what to do.

  8. The empty state is the onboarding UX

    Zero journeys: a muted map, one sentence, one button — “Log your first journey”. It is the first thing anyone sees; design it like it matters, because it does.

  9. Edit and delete without dialogs UX

    Swipe or long-press in the journey list. Delete gets an undo toast, never a confirm box.

Phase 4

Backend

Supabase, kept deliberately small. The schema file already exists — this phase is mostly wiring, not building.

  1. Project + schema BE

    Create the Supabase project, paste supabase/schema.sql — journeys table, derived stats view, row-level security already written.

  2. Google sign-in only BE

    One OAuth provider, one redirect URL, done. No password reset flow to build, ever.

  3. Row-level security, on BE

    Explained simplyNormally your frontend asks the database “give me journeys where user = me”, and a bug in that query could leak someone else’s rows. Row-level security moves the rule into the database itself: a policy saying a request may only ever see rows whose user_id matches the logged-in user. After that, even a buggy query physically cannot return another person’s journeys. The database is the bouncer, not your code.

  4. Server state via TanStack Query FE

    useJourneys() for the cached list; useAddJourney() as the optimistic mutation, computing distance_km from the routing graph at save time.

  5. Signed-out is a demo, not a wall UX

    Signed out, the map shows the sample journeys greyed with one sign-in button. The app demonstrates itself before asking for anything.

  6. The one AI feature BE

    An Edge Function that turns pasted ticket text into {from, to, date, train}, validated with zod.

    Explained simplyAn Edge Function is a tiny piece of server code Supabase runs for you on demand — one file, they host it. It exists here for exactly one reason: the AI key must live on a server, because anything shipped to the browser is readable by anyone who opens devtools. The browser sends the pasted text to your function; the function holds the key, calls the model, checks the reply, returns clean fields.

  7. Rate-limit that function BE

    A per-user counter in the database, so a leaked URL cannot run up your bill.

  8. Export my data FE

    One button, JSON or CSV, straight from the client. It is your data, and it makes the not-a-walled-garden point cheaply.

Phase 5

Rewards and the passport

Where the reward-loop reading gets applied — honestly. Nothing here rewards opening the app; everything rewards having gone somewhere.

  1. Stat tiles that hold still UX

    Equal widths (fixes the reflow finding), cream tabular numerals, counts animating over 300ms so 999 → 1,000 is a moment instead of a jolt.

  2. States unlocked, honestly capped UX

    Fill animates over 400ms with a one-line toast naming the state. Say “9 of 29 reachable” — seven states have no station in the data, and admitting that beats pretending 36 is reachable.

  3. Milestones with real thresholds UX

    1,000 km · 10 stations · 5 states · one journey over 24 hours · both coasts. Locked ones visible, so there is something to aim at. No badge for signing up, ever.

  4. The passport card UX

    Canvas-rendered at 2×: mini-map of your routes, the three big numbers, the station-board aesthetic, the date. navigator.share on mobile, download on desktop. This is the thing that gets posted.

  5. The journey log screen UX

    Reverse-chronological, each entry a small board-style row — doubling as the accessible list view from Phase 2.

Phase 6

DevOps and quality

Deliberately light. No CI beyond the host, no error service, no Docker — per the decisions doc.

  1. Vercel + a real domain OPS

    Connect the repo, set the two VITE_ variables, deploy. Every push ships; every pull request gets a preview URL.

    Explained simplyA preview deploy is a full copy of your site built from a branch, living at its own temporary address — so you check a change on your actual phone before merging it, not after.

  2. Decide where generated data lives OPS

    Either commit the 1.1 MB of generated assets, or run npm run assets in the build step. Both are defensible; pick one and write it in the README.

  3. Offline that actually helps FE

    The service worker already caches the shell and stations. Add a queue for journey saves made offline, synced when the connection returns — trains are the one place your users predictably have no signal, so this is on-subject, not gold-plating.

    Explained simplyA service worker is a small script the browser keeps even after the tab closes. It sits between your app and the network and can answer requests from its own cache — which is why the app can open instantly in a tunnel, showing the map from the last time it loaded.

  4. A performance budget in writing OPS

    Lighthouse ≥ 95 · first paint under 1s · zero layout shift · 60fps pan on a mid-range Android. Re-measure after every phase, not once at the end.

  5. Tests where they pay OPS

    Vitest on the pure functions only: distance, projection, shortest-path on a toy graph, the pipeline filters. No component tests in v1.

  6. Fail like a person UX

    An error boundary with a human screen — “The map hit a problem; reload usually fixes it” — instead of a white page.

Phase 7 — week 6

The Polish Pass

No new features. Run the protocols — squint, greyscale, flip, 400% zoom, computed styles, 10× slow-motion, hostile content, real phone outdoors, cold open, annotate-before-fixing — and fix in severity order. Re-score the nine dimensions; the delta from 19/45 is the week’s output. Then the case study, the 30-second capture, the public post, and the link to Vidit.

Phase 8

The ideas shelf

Good-to-haves in rough value order. Nothing here starts before v1 ships — when an idea arrives mid-work, it lands here and waits.

  1. Hindi / English toggle UX

    Deeply on-brand — station boards are bilingual by law. Tier 1 (cheap): the board component always shows both scripts, names via a lookup file. Tier 2: UI strings in en.json / hi.json behind a tiny t('logJourney') helper.

    Explained simplyTranslation frameworks mostly solve problems you do not have — plurals across twelve languages, right-to-left layouts. For two languages and about forty strings, a JSON file per language and a function that picks from it is the entire system. Indian number formatting (1,00,000) you already get from toLocaleString('en-IN').

  2. Zoom-to-journey UX

    Tap a log entry, fly to its bounding box. Costs an afternoon once fly-to exists.

  3. Replay my year UX

    All routes drawing in chronological order — the passport card’s animated sibling, and extremely shareable in December.

  4. Railfan layer UX

    Zones coloured, divisions outlined, junctions emphasised. The audience that will actually find this app, served with data already in hand.

  5. Paste-a-ticket as the primary flow BE

    Once the Phase 4 parser has earned trust, promote it; manual entry stays one tap away.

  6. Sound and haptics, off by default UX

    A soft station-bell tick on unlock, a 10ms vibration on save. Sound in an interface is trespassing unless invited — so it is a setting, and it starts off.

  7. Night-run rendering UX

    Overnight journeys draw with a subtly different treatment — the data is already in the date field.

  8. GPX / GeoJSON export FE

    An afternoon of work that delights exactly the railfan audience.

  9. Named, so it stays said no to —

    Streaks and daily-use mechanics: never — the honest reward is the map. Friends and leaderboards: no — comparative reward changes what the map means. Photos: v2 at the earliest — storage, moderation and layout are a big feature in a trench coat. Native widgets and share-sheet: only if daily use proves out, via a wrapper.

Two implementation notes. Only tokens change between these — the code never mentions a hex, so a whole theme is a ~15-line block in tokens.css. And the red “you are here” stays in the same family across all three, because meaning-colours should survive re-theming: if the semantic colours changed with the mood colours, the map would have to be relearned per theme. In Vande Bharat, note the full saffron #E8720C is a fill only (navy text on top) — as text it fails contrast, the same rule the board yellow follows in the light theme today.

How to use this: each evening, open the current phase, pick the top unchecked item, do only it. Ideas that arrive mid-work go to Phase 8 — never into the current phase. The list is exhaustive precisely so that nothing new deserves to jump the queue.
