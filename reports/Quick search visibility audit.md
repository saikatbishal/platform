# Zero journeys hide the magnifier, by design

The quick-search magnifier is not broken. It is hidden on purpose, because the app thinks you have **zero journeys**. The button renders only under `mine > 0`, where `mine = store.journeys.length`, and it shares that gate with Milestones and Rail pass ([src/App.tsx:65, 449, 479, 496](../src/App.tsx)). Once `.env` held real Supabase values, the app switched to live mode. When you are signed in, it now reads journeys only from the Supabase `journeys` table. Every journey you logged while signed in to demo mode lives under a localStorage key for the fixed demo user, `platform.journeys.v1.00000000-0000-4000-8000-000000000001`. **No code path in live mode reads or migrates that key** ([src/features/journeys/useJourneys.ts:28-35, 73](../src/features/journeys/useJourneys.ts); [src/features/journeys/journeyStorage.ts:109-118](../src/features/journeys/journeyStorage.ts)). The live table exists, but it has none of your rows: an anonymous GET returned HTTP 200 with `[]`. The "old copy works perfectly" comparison proves less than it seems to. **`kuchbhi/platform` has never contained quick search** in any commit, branch, stash or file. It uses the same `.env` values, the same config and the same dependencies. It cannot show a magnifier, so it has nothing to fail at. It also reads from the same Supabase project, so signed in, it would show the same zero count. The fix is to get your demo journeys into your live account. Separately, the audit found real data-loss bugs on the live path, and found that the quick-search feature exists only as uncommitted files.

## One gate, `mine > 0`, controls three pieces of UI at once

The button itself has no condition. It is mounted in two places: a desktop row visible at 640px and wider, and a phone column above `+`. Both are wrapped in `{mine > 0 && findJourney}`. The `/` keyboard shortcut returns early when `mine === 0` ([src/App.tsx:127, 215-241, 477-498](../src/App.tsx)). Every other way the button could vanish was checked and ruled out. Its colour classes (`bg-surface`, `border-line`, `text-ink-soft`) map to tokens defined in both themes. Milestones and Rail pass use the same classes ([src/styles/index.css:37-75](../src/styles/index.css); [src/styles/tokens.css](../src/styles/tokens.css)). No permanent layer covers the bottom corners. The z-indexed elements are either transient sheets and tooltips or sit in the top corners ([src/features/map/IndiaMap.tsx:518, 920](../src/features/map/IndiaMap.tsx)). **Typecheck and production build both pass**, and the built bundle contains "Find a journey" and two `data-find-button` hits. `FindJourneySheet` mounts only when `findOpen` is true, so it cannot stop the button from rendering. There is no error boundary, so a render error would blank the whole app, not remove one button ([src/main.tsx](../src/main.tsx)). That leaves a test you can run without DevTools: **if Milestones and Rail pass are also missing, `mine === 0` is confirmed.**

## Live mode reads a different bucket from the one demo mode filled

The mode is fixed at module load. `isSupabaseConfigured` is true when neither value is empty, contains `YOUR_` or `__FILL`, or ends in `...`. Your `.env` values (40 and 46 characters) pass that check ([src/lib/supabase.ts:16-25](../src/lib/supabase.ts); [src/features/auth/useAuth.ts:8](../src/features/auth/useAuth.ts)). The routing switch is `useSupabase = isSupabaseConfigured && userId !== null`, so the data source depends on both the mode and whether you are signed in:

| State | Where journeys are read from |
|---|---|
| Demo, signed out | localStorage `platform.journeys.v1.anon` |
| Demo, signed in | localStorage `platform.journeys.v1.0000…0001`, after anon has been drained into it |
| Live, signed out | localStorage `platform.journeys.v1.anon` |
| Live, signed in | Supabase `journeys where user_id = <real id>`, plus anon merged in and uploaded |

([src/features/journeys/useJourneys.ts:28-35, 59-125](../src/features/journeys/useJourneys.ts); [src/features/auth/demoSession.ts:14-19](../src/features/auth/demoSession.ts))

The trap is the demo sign-in flow. **Signing in to demo mode already moved your anon journeys into the demo key and emptied anon** (`mergeJourneys(read(key), anon)`, `write`, `commit`) ([src/features/journeys/useJourneys.ts:113-124](../src/features/journeys/useJourneys.ts)). The only migration source in `src/` is `takeAnon()`, which reads `ANON_KEY` and nothing else ([src/features/journeys/journeyStorage.ts:109-118](../src/features/journeys/journeyStorage.ts)). So after going live, you read zero both ways. Signed out, the anon bucket is empty. Signed in, Supabase never received the demo rows. A comment in `demoSession.ts` says the switch "changes where the id comes from and nothing else". That is true of the id. It is not true of the data ([src/features/auth/demoSession.ts:6-13](../src/features/auth/demoSession.ts)). One exception: any journeys logged in demo mode while signed out, and never followed by a demo sign-in, are still in anon. They would upload on your first live sign-in.

## The alternatives were each tested; none displaces the conclusion

**A stale demo bundle** is not the cause, and would produce the opposite symptom. A leftover `platform.demo-session = 'open'` flag is read only inside the `if (!supabase)` branch, so live mode ignores it ([src/features/auth/useAuth.ts:77-81, 91-112](../src/features/auth/useAuth.ts)). The go-live doc warns that an unrestarted dev server keeps demo mode ([docs/09-auth-go-live.md:165](../docs/09-auth-go-live.md)). But Vite 8.2.2 restarts itself when `.env` changes ([node_modules/vite/dist/node/chunks/node.js:27009-27019](../node_modules/vite/dist/node/chunks/node.js)). And a stuck demo mode would *show* the demo bucket, which would make the button appear. **A service worker** cannot serve old code to `npm run dev`. vite-plugin-pwa skips registration in dev when `devOptions` is unset, and `dist/` was rebuilt after the quick-search files anyway ([node_modules/vite-plugin-pwa/dist/index.js:294, 314, 810](../node_modules/vite-plugin-pwa/dist/index.js); [vite.config.ts:16-56](../vite.config.ts)).

**A different origin** is a real, independent route to zero, and it stacks with the main cause. localStorage is keyed by scheme, host and port. The `/platform/` base path does not partition it. `vite.config.ts` asks for port 5173 without `strictPort`. If another copy is already running, the second one silently lands on 5174 with an empty store. `vite preview` (4173), `127.0.0.1` and a LAN IP are also separate origins ([vite.config.ts:10, 61](../vite.config.ts)). Google sign-in is also pinned to `http://localhost:5173` ([supabase/config.toml:11](../supabase/config.toml); [docs/09-auth-go-live.md:88, 107-108](../docs/09-auth-go-live.md)). A sign-in started from another port therefore lands its session back on 5173. **A failed Supabase read** is the last candidate: every error becomes `[]`, which is indistinguishable from "none" (see the next section). The anonymous 200 rules out a missing table. It cannot rule out a missing column or a failure specific to your authenticated session.

## The old copy never had a magnifier to show

`kuchbhi/platform` is on `main` at `e9995f9` (PR #12), plus uncommitted form work that later became PR #14. A `git grep` across every ref and the stash for `FindJourney`, `searchJourneys`, `data-find-button` and `quick-search` returned nothing ([kuchbhi git history, `e9995f9`](../../kuchbhi/platform)). Ignoring line endings, these files are byte-identical between the copies: `package.json`, `vite.config.ts`, `index.html`, `src/main.tsx`, `src/lib/supabase.ts`, `useJourneys.ts` and `journeyStorage.ts`. `npm ls` shows the same top-level versions in both. **Both `.env` files hold the same two values** (matching SHA-1 prefixes `7c488a62d346` and `4b624298b5b6`), so both run live against the same project. In the old copy, "working" can only mean the journey-gated chrome that does exist there appears: Milestones and Rail pass under `{mine > 0 && …}`, and a "+" that reads "Add a journey" rather than "Add your first journey" ([kuchbhi/platform/src/App.tsx:63, 132-133, 348](../../kuchbhi/platform/src/App.tsx)).

That creates a testable contradiction. Suppose the old copy shows journeys **right now**, on `localhost:5173`, in the same sign-in state as the new one. Then it is reading the same data through the same code, and it should show zero too. If it does show journeys, one of the following is true. It is being viewed on a different origin, whose localStorage still holds data. Or it is signed out while an anon bucket there still has rows. Or the impression dates from before `.env` was filled, when it was in demo mode. The notes cannot tell which, because neither app was run in a browser. What they do establish: **nothing in the code, config or dependencies differs in a way that could make one copy show a journey count the other hides.**

## Secondary bugs and repository risk (separate from the visibility question)

These are not why the button is hidden today. They will make the fix harder to verify, and can lose data during it. **No code changes were made. These are findings only.**

**Silent read failure.** On any error, `readFromSupabase` logs `[journeys] Supabase read failed:` and returns `[]`. The hook then sets `loaded: true`. A missing column, an RLS rejection or a network drop therefore shows up as "you have no journeys" ([src/features/journeys/journeyStorageSupabase.ts:50-53](../src/features/journeys/journeyStorageSupabase.ts); [src/features/journeys/useJourneys.ts:64-76](../src/features/journeys/useJourneys.ts)). This breaks the project rule against silently dropping a journey.

**`addToSupabase` returns `null` instead of throwing.** Two consequences follow. First, the anon-to-account migration loop awaits each insert and then calls `commit()`. Its `catch` fires only on a throw, so **the anon bucket is emptied even when every insert was rejected**. That is the opposite of the code's own comment, "a partial failure has to leave the anonymous bucket untouched". Second, optimistic adds use `.catch(rollback)`, which never fires. A rejected journey shows until reload, then disappears. `removeFromSupabase` returns `false` and has the same flaw ([src/features/journeys/useJourneys.ts:85-100, 146-156, 172-180](../src/features/journeys/useJourneys.ts); [src/features/journeys/journeyStorageSupabase.ts:64-95](../src/features/journeys/journeyStorageSupabase.ts)). Several things can trigger a rejection:

- the `from_code <> to_code` and `travelled_on <= current_date` checks, and the RLS `with check` ([supabase/schema.sql:9, 34-35, 47-50](../supabase/schema.sql));
- non-uuid fallback ids, minted when `crypto.randomUUID` is absent, as on a phone reaching the dev server over plain-http LAN ([src/features/journeys/useJourneys.ts:136-139](../src/features/journeys/useJourneys.ts));
- a table created before commit `6264bfb`, which added the three time columns inside `create table if not exists`. Re-running the schema would never add them. This is unverified; the check below settles it.

**The feature exists in one place only.** `feat/quick-search` points at the same commit as `main`, and no remote branch exists. `FindJourneySheet.tsx`, `searchJourneys.ts` and `scripts/check-search.ts` are untracked. The `App.tsx` changes (+175 lines) and the `AddJourneyForm.tsx` `initialFrom` prop are uncommitted. Losing this working tree loses the feature. Separately, the `docs/*` and `docs/brand/*.svg` "modifications" are LF-to-CRLF churn only, and the `package-lock.json` diff only rewrites metadata. Two stale notes also need correcting. The comment at `src/App.tsx:44-49` still says journeys are in localStorage. `CLAUDE.md` still describes `sampleJourneys.ts`, which no longer exists.

## Confirm it in DevTools, then fix it

Run these on the same tab where the button is missing, at `http://localhost:5173/platform/`:

| # | Check | What it tells you |
|---|---|---|
| 1 | Look at the address bar port. Is it `5173`? | Another port (5174, 4173) or `127.0.0.1` has its own empty storage. |
| 2 | Are Milestones and Rail pass visible? | If not, `mine === 0` is confirmed and the button is hidden by design. |
| 3 | `Object.keys(localStorage).filter(k => k.startsWith('platform.'))` | Look for `platform.journeys.v1.00000000-0000-4000-8000-000000000001`. |
| 4 | `JSON.parse(localStorage.getItem('platform.journeys.v1.00000000-0000-4000-8000-000000000001') ?? '[]').length` | Counts the stranded demo journeys. |
| 5 | Same, with key `platform.journeys.v1.anon` | Should be 0 if a demo sign-in drained it. |
| 6 | Console: filter for `[journeys]` | Any `Supabase read failed` or `insert failed` means the silent-failure path, not just an empty table. |
| 7 | Network tab after sign-in: the `journeys?select=*&user_id=eq.…` response | `200 []` means the table is empty for you. 4xx means a schema or RLS problem. |
| 8 | Visit `<SUPABASE_URL>/rest/v1/journeys?select=departure_time,arrival_time,arrival_day_offset&limit=0` with the publishable key | A 400 means the live table is missing the time columns, and every insert will be rejected. |

If check 4 returns a number above zero, that is your data and your answer. **Back it up before anything else.** Run `copy(localStorage.getItem('platform.journeys.v1.00000000-0000-4000-8000-000000000001'))` and save the clipboard to a file. Because of the migration bug, first make sure the schema is complete (check 8). If it is not, run the missing `alter table … add column` statements in the Supabase SQL editor. Then, while signed out in live mode, copy the demo value into `platform.journeys.v1.anon` and reload: the journeys and the magnifier should appear. Then sign in, and the existing `takeAnon` path uploads them to your account. Afterwards, confirm the rows in the Supabase table editor *before* trusting that anon is safely empty. If you have no journeys anywhere, add one while signed in and reload. If it survives the reload, the live path works and the button will appear. If it vanishes, you have hit the swallowed-insert bug, and the console will name the rejection. Finally, commit or at least stash the quick-search files so the feature does not live in a single working tree.

## Conclusion

The absent button is a symptom of a data problem. It is not a UI bug. The demo-mode design keeps its promise about ids ("the switch changes where the id comes from") and quietly breaks it about data. That gap stayed invisible because every read failure and every rejected write also becomes a plausible-looking zero. So the real risk is not this one hidden button. The app currently cannot distinguish "you have no journeys" from "we lost your journeys". It can also turn the second into the first during the very migration meant to protect them. Until reads surface their errors and `addToSupabase` fails loudly, any go-live check that relies on "the count looks right" is unreliable. The old-copy comparison teaches something similar. Two trees with identical config and identical `.env` cannot legitimately disagree about a journey count. When they seem to, the difference is in the browser (origin, sign-in state, timing), not in the code.
